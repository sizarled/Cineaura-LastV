# الانتقال الآمن إلى Supabase Auth — إصلاح P0

**الحالة: مرشّح إصلاح في المستودع، غير مطبّق على الإنتاج.**

تاريخ التوثيق: 2026-10-24. هذا العمل يبدأ بمعالجة انتحال الهوية وكشف الحسابات والصلاحيات. لا يغلق بقية نتائج `site-audit-report-ar.md`، ولا يعني أن الموقع المنشور أصبح آمنًا. لم تُنفّذ ملفات SQL التالية على المشروع الحي، ولم تتغير إعدادات Auth أو بيانات أعضائه أو نشر الموقع بهذا العمل.

## 1. ما تغير

- أصبحت كلمة المرور وتأكيد البريد والاستعادة وتغيير البريد عبر **Supabase Auth / GoTrue**. أُزيلت قراءة كلمات مرور الأعضاء ورموز الاستعادة من المتصفح ومسارات الدخول القديمة الاحتياطية.
- يعتمد ربط الحساب على `auth.uid()` وبريد **مؤكد في `auth.users`**. لا يُقبل `member_id` أو الدور أو الرصيد من `localStorage` أو `user_metadata` كدليل هوية.
- يخزن `cineaura_session` بيانات عرض مرتبطة بمعرّف Auth فقط؛ مصدر الصلاحيات هو JWT الذي تتحقق منه البنية الخلفية وسياسات قاعدة البيانات، وليس هذا التخزين.
- يستخدم تأكيد البريد والاستعادة وتغيير البريد PKCE مع حالة عشوائية ومعرّف تحقق صالح لساعة. يجب فتح الرابط في **المتصفح نفسه الذي بدأ الطلب**؛ يمكن فتحه في تبويب جديد. لا تُقبل جلسات implicit المرسلة داخل تجزئة URL.
- يتطلب إنشاء/تغيير كلمة المرور 12–256 محرفًا في الواجهة. **يجب فرض الحد الأدنى والسياسة على GoTrue أيضًا**؛ التحقق في المتصفح وحده ليس حاجزًا أمنيًا.
- يحافظ ربط العضو القديم على معرّفه ومحتواه ونقاطه وحقول حسابه. لا يُنشئ نسخة بديلة من العضو عند تعذر إثبات ملكيته.
- يمنع cutover قراءة كلمات المرور ورموز الاستعادة من أدوار المتصفح، بما فيها صاحب الحساب والموظفون، ويلغي منح الأعمدة القديمة وسياسات الوصول العامة غير المراجعة.
- تُعرض البيانات العامة من `member_directory` و`profile_directory` و`staff_directory`. تُحجب البيانات الشخصية بحسب صاحب الحساب/إذن Accounts، وتُستبعد أعمدة الملفات الشخصية الجديدة غير المدرجة صراحةً في قائمة السماح.
- تُربط عمليات RPC ذات الفاعل بالعضو الأصلي، ورموز الموظفين بصاحب جلسة Auth. تُعطّل دوال الدخول/الاستعادة/إنشاء Super Admin القديمة والدوال غير المعروفة للمستخدمين. توجد قائمة سماح للتواقيع الكاملة؛ لا يكفي أن تضيف دالة مجهولة معاملًا باسم `p_member` أو `p_token`، ولا يرث overload جديد امتيازات دالة أصلية بالاسم نفسه.
- تُلغى جلسات لوحة الإدارة القديمة أثناء الاحتواء الأولي وقبل فتح ربط الحسابات، ويعيد أول cutover إبطال أي جلسة أُنشئت إداريًا أثناء التحضير. إعادة تطبيق cutover المغلق لا تُلغي جلسات الموظفين الجديدة. لا يُفتح دخول الموظفين قبل مراجعة مستقلة لقائمة أدوارهم وصلاحياتهم.
- الرسائل محصورة بأطرافها، وأسماء المرسل والمتلقي تُشتق من سجلات الخادم لمنع انتحال الأسماء المخزنة في المتصفح. الإشعارات محصورة بالمتلقي ولا يسمح بإنشائها اعتباطيًا من العميل.
- تعديل النصوص المسموحة في الملف الشخصي منفصل عن عدادات المشاهدة والنقاط والخطة والحالة. السحب يتطلب إعادة تحقق بكلمة المرور الأصلية عبر GoTrue خلال آخر خمس دقائق؛ لا تُقبل بصمة كلمة المرور القديمة كإثبات.

## 2. الملفات وترتيبها

| الملف | الدور |
|---|---|
| `js/auth.js` | نقل Auth والجلسات والتجديد وPKCE؛ بلا مكتبة تشغيل خارجية |
| `js/common.js` | الطلبات الموثقة، ربط بيانات العرض، تحميل العضو ورسائل الخطأ |
| `login.html` / `register.html` / `rest.html` وملفات JS التابعة | الدخول بالبريد، ربط الحساب القديم، استكمال حساب مؤكد، الاستعادة |
| `sql/auth_contain.sql` | أولًا: تجميد صلاحيات المتصفح القديمة وإبطال رموز الموظفين قبل التقاط أدلة الملكية ومراجعة الامتيازات |
| `sql/auth_prepare.sql` | إنشاء خريطة UUID وسجل المطالبات الخاص والدوال الأصلية وواجهات القراءة الآمنة |
| `sql/auth_cutover.sql` | إغلاق المنح والسياسات القديمة، تغليف RPC واحتواء Storage |
| نسخ `.txt` الثلاث | مرايا مطابقة لملفات SQL؛ **ليست مراحل إضافية للتنفيذ** |
| `tests/auth-client.test.cjs` | اختبارات نقل Auth بموفر تجريبي |
| `tests/security-db.test.cjs` | اختبارات الصلاحيات على PostgreSQL مؤقت، باستخدام ملفات المخطط الفعلية وبيانات اصطناعية |
| `tests/auth-browser.test.cjs` | صفحات الموقع الفعلية داخل Chromium، مع اعتراض جميع الطلبات |
| `tests/auth-source.test.cjs` | تحليل الصياغة وترتيب الاعتمادات والمرايا والترجمات وعدم عودة المسار القديم |

**الترتيب إلزامي: احتواء ثم تحضير ثم إغلاق نهائي. ملف التحضير وحده ليس ترقية إنتاج.** يرفض التحضير العمل دون علامة الاحتواء الأولي. لا تنشر الواجهة الجديدة منفردة على قاعدة قديمة، ولا تنفّذ cutover على موقع عامل بواجهة قديمة دون وضع الصيانة.

تبقى ملفات التثبيت القديمة ضرورية لبناء قاعدة اختبار من الصفر، لكنها تحتوي سياسات قديمة مفتوحة. يجب تنفيذ `auth_contain.sql` ثم التحضير ثم cutover **بعد** ملفات المخطط المطلوبة، وعدم إعادة تشغيل المثبتات القديمة بعد الإغلاق. حدّث أي دليل تثبيت/أتمتة قبل السماح بإصدار آخر.

## 3. شرط ملكية الحساب القديم — ممنوع التجاوز

كان البريد والحساب قابلين للتعديل دون هوية موثقة في النظام القديم؛ لذلك لا يكفي أخذ البريد الحالي ثم الوثوق به تلقائيًا.

1. بعد إيقاف المنح القديمة بـ `auth_contain.sql`، يلتقط `auth_prepare.sql` العناوين في `cineaura_private.legacy_member_claims`، **دون اعتماد أي صف**.
2. راجع كل ربط على حدة باستخدام نسخة موثوقة سابقة للتعرض، أو تحقق مستقل من المالك. كون العنوان موجودًا في الجدول الحالي، أو امتلاك بصمة كلمة المرور أو رمز الاستعادة القديم، ليس دليلًا كافيًا.
3. سجّل مرجع دليل غير فارغ في `approval_reference` مع `approved_at` من اتصال إدارة موثوق فقط. لا تضف جدول المطالبات أو مخطط `cineaura_private` إلى مخططات PostgREST المكشوفة.
4. على المستخدم إثبات البريد عبر Auth أيضًا. أول ربط لبريد مؤكد **قبل التقاط السجل** يتطلب تأكيدًا جديدًا أو AMR أصليًا موقعًا من GoTrue بطريقة `otp`/`recovery` بعد الالتقاط وخلال 15 دقيقة. `user_metadata.amr` غير مقبول. يمكن للمستخدم صاحب حساب Auth سابق استخدام استعادة كلمة المرور لإثبات الملكية مجددًا.
5. التعارضات والتكرارات والعناوين غير الموثوقة تبقى معلقة للمراجعة. لا تعتمد السجل دفعة واحدة، ولا تغيّر `captured_at` إلى الماضي لتجاوز التحقق، ولا تربط استنادًا إلى معرّف يرسله المتصفح.
6. إذا احتاج عنوان ملتقط إلى تصحيح، افعل ذلك فقط وفق الدليل المستقل، وسجّل التصحيح واطلب إثبات بريد جديد بعده. إعادة تشغيل التحضير لا تستبدل العناوين الملتقطة.

قالب المراجعة التالي **ليس أمرًا جاهزًا للتطبيق العام**؛ متغيراته يجب أن تأتي من مراجعة المالك، لا من نموذج الموقع:

```sql
UPDATE cineaura_private.legacy_member_claims
   SET approved_at = now(), approval_reference = :independent_evidence_reference
 WHERE member_id = :independently_verified_member_id
   AND email = :independently_verified_normalized_email
   AND approved_at IS NULL
RETURNING member_id;
```

قد توقف العناوين المكررة بعد التطبيع تحضير السجل بقيد uniqueness. حلّها بالمراجعة، لا بحذف أعضاء أو تغيير معرّفاتهم أو اعتماد أحدهم اعتباطيًا. اطلب كلمات مرور **جديدة وفريدة**، لا إعادة استخدام كلمات المرور القديمة التي ربما تعرضت.

### قائمة الموظفين نفسها تحتاج إثباتًا مستقلًا

كانت صفوف `staff` قابلة للكتابة أيضًا؛ لا يكفي أن تحمل جلسة Auth صحيحة لتصبح قيمة `super` القديمة موثوقة. بعد الاحتواء وقبل cutover:

1. طابق العضو والدور والأقسام وكلمة مرور الدور المجددة لكل موظف مع سجل إداري موثوق. صحح أي امتيازات غير مثبتة من اتصال الإدارة، ولا تستنتج صحة الدور من الجدول المكشوف سابقًا.
2. سجّل مرجع المراجعة وبصمة القائمة بعد اكتمال الفحص. المثال التالي **لا يُنفذ قبل المراجعة المستقلة**:

   ```sql
   UPDATE cineaura_private.auth_rollout
      SET staff_review_reference = :independent_staff_review_reference,
          staff_review_fingerprint = cineaura_private.staff_roster_fingerprint()
    WHERE id;
   ```

3. يقفل cutover قائمة الموظفين أثناء فحص البصمة وتغيير المنح؛ يرفض قائمة بلا مرجع أو قائمة تغيرت بعد المراجعة. بعد أي تعديل شرعي لاحق في دور/قسم/كلمة مرور موظف، يلزم تحديث المراجعة قبل **إعادة** cutover أيضًا.
4. لا تُنسخ صفوف الموظفين أو بصمات كلمات مرورهم إلى Git أو المخرجات العامة. لا يثبت ربط البريد سلامة الأرصدة أو الخطط أو حالات الحساب التي كانت قابلة للتعديل؛ راجع سلامتها جنائيًا من النسخة الموثوقة ولا تصفرها اعتباطيًا.

## 4. بوابات لازمة قبل الإنتاج

لا تنتقل إلى الإنتاج حتى تتحقق جميع النقاط التالية:

- [ ] تحديد النطاق الحقيقي ونافذة صيانة مع منع وصول الجمهور إلى الموقع و**API وStorage** القديمين؛ صفحة صيانة للواجهة وحدها لا تمنع استدعاء API مباشرة.
- [ ] نسخة احتياطية موثوقة لقاعدة البيانات والمنح والسياسات والدوال وبيانات/إعدادات Storage؛ اختبار الاستعادة وعزل النسخة بعيدًا عن خادم الملفات العام وGit.
- [ ] تجهيز مشروع Staging معزول، لا تستعمله حسابات أو مفاتيح أو عمليات مالية حقيقية. بيانات الاختبارات المضافة اصطناعية، وليست نسخة من رسائل المستخدمين.
- [ ] مطابقة مخطط Staging مع الإنتاج، بما فيه اختلافات الدوال والامتدادات والمالكين. الاختبار المحلي لا يغطي كل انحراف في المشروع الحي.
- [ ] جرد العمليات الخلفية والوظائف المجدولة ومفاتيح الخدمة وعناوين Edge. التحقق من أن الوظائف الموثوقة فقط تحمل `service_role`؛ لا يدخل هذا المفتاح HTML/JS أو السجلات أو الدردشة.
- [ ] مراجعة سجل ملكية الحسابات وقائمة امتيازات الموظفين وتوثيق الدليل المستقل، خاصة حساب Super Admin؛ سلامة البيانات التاريخية تحتاج مراجعة أيضًا.
- [ ] ربط Super Admin معروف بــ Auth مؤكد، والتحقق من أنه غير محظور ويمكنه فتح اللوحة. لا يوجد bootstrap عام بديل. تجهيز وصول إداري آمن للطوارئ خارج المتصفح.
- [ ] تدوير كلمات مرور الموظفين/الأسرار التي يُحتمل تعرضها وإلغاء الجلسات غير الموثوقة وفق خطة استجابة للحادث. لا ترسل كلمات المرور أو الرموز في الدردشة.
- [ ] اختبار البريد الحقيقي وPKCE وJWT وPostgREST على Staging، ثم اجتياز مصفوفة الميزات أدناه أو تعطيل الميزات غير المراجعة صراحةً.
- [ ] موافقة تشغيلية واضحة على نافذة الانتقال والتحقق وخطة التراجع. لا يُعد نجاح `npm test` موافقة على تعديل الإنتاج.

### إعدادات Supabase Auth المطلوبة

**لا يغير نشر الواجهة على نطاق Staging وجهة قاعدة البيانات تلقائيًا.** لا تزال قيم `SUPABASE_URL` و`SUPABASE_KEY` في `js/common.js` موجهة للمشروع الموجود. قبل أي تجربة اتصال حقيقية، جهّز نسخة نشر Staging تشير إلى URL ومفتاح **publishable** لمشروع الاختبار المعزول، وعدّل أيضًا رابطَي قوائم IPTV الافتراضيين في الملف نفسه أو عطلهما في تلك النسخة. لا تستخدم مفتاح `service_role` في الواجهة. افحص Network للتأكد من عدم بقاء أي طلب نحو مشروع الإنتاج؛ لا تفتح خادم معاينة متصلًا بالإنتاج لاختبار التسجيل أو الكتابة. الاختبارات المحلية المضافة آمنة دون هذا التعديل لأنها تعترض كل طلب.

غيّر الإعدادات على **Staging أولًا** عبر لوحة Supabase/إدارة موثوقة:

- فعّل تسجيل البريد وتأكيد البريد؛ **Auto-confirm معطّل**. يرفض العميل التسجيل الذي يرجع جلسة تلقائية بدل تأكيد البريد.
- اجعل Site URL نطاق HTTPS الصحيح، وأضف روابط العودة المحددة لـ `login.html` و`rest.html` مع دعم معامل `auth_state` العشوائي. اختبر مطابقة أنماط Redirect Allow List فعليًا؛ لا تسمح بأي نطاق/منفذ/مسار عشوائي ولا Redirect مفتوح.
- عناوين العودة مشتقة من أصل الصفحة، وتدعم مسار تثبيت فرعيًا؛ جرّب عنوان النشر الحقيقي لا `localhost` من متصفح المستخدم. لا تستخدم الأصل التجريبي `cineaura.test` في الإنتاج.
- اضبط SMTP والنطاق/المرسل، حدود إرسال البريد، سياسة كلمات المرور بحد أدنى 12، والحماية من كلمات المرور المكشوفة إن كانت متاحة. اختبر تأكيد تغيير البريد الآمن وعدم تحريك عنوان العضو قبل إتمامه.
- راجع عمر JWT وتجديد الجلسات والحماية من إساءة الاستخدام. إبطال refresh token لا يلغي كل JWT مصدر فورًا؛ لا تعتمد على logout وحده لإيقاف مستخدم محظور. دوال الهوية تفحص حالة العضو في قاعدة البيانات.
- احتفظ بإعدادات المخططات المكشوفة كما يلزم للتطبيق، ولا تكشف المخطط الخاص أو `auth` عبر PostgREST.

لم تُعدّل إعدادات Auth الحية بهذا الإصلاح. الإعدادات المرصودة أثناء التدقيق كانت Site URL محليًا وقائمة عودة فارغة؛ يجب إعادة التحقق منها عند التنفيذ، لا افتراض بقائها أو صلاحيتها.

## 5. تجربة Staging ثم الانتقال

1. ابنِ Staging بالمخططات المطلوبة أولًا، وراجع كل سياسات/دوال التثبيت القديمة. للاختبارات المؤقتة ترتيب مخطط ثابت في `tests/security-db.test.cjs`؛ هذا ليس مثبت إنتاج عامًا.
2. ابدأ وضع الصيانة. من اتصال إدارة موثوق، وفي **الطلب نفسه**، ضع الإقرار التالي ثم كامل `sql/auth_contain.sql`:

   ```sql
   SET cineaura.allow_security_containment = 'on';
   -- يلي ذلك كامل sql/auth_contain.sql.
   ```

   هذا توقف مقصود للوصول القديم، لا تحديث بلا توقف. يسحب امتيازات الجداول والأعمدة وRPC القديمة من أدوار المتصفح ويبطل رموز الموظفين قبل التحضير، مع إبقاء صيانة `service_role`. تحقّق من الرفض عبر API نفسه؛ ليست صفحة الصيانة بديلًا عنه. لا تعاود تشغيل أي مثبت مخطط قديم بعد هذه الخطوة.
3. نفّذ `sql/auth_prepare.sql` كاملًا. لا تنشر سجل المطالبات أو مخرجات بياناته. يمكن تكرار التحضير أثناء هذه المرحلة فقط؛ بعد `sealed` يُرفض منعًا لإعادة تعريف أغلفة RPC أو فتح مسار قديم عرضًا.
4. راجع ملكية الحسابات وقائمة الموظفين بصورة مستقلة، وسجّل المراجع والبصمة. اعتمد حساب الاختبار/المشرف فقط بعد المراجعة. استخدم بريدًا تجريبيًا تملكه فعليًا، وأنهِ تأكيد Auth ثم `member_auth_bind()` بجلسة المستخدم الحقيقية. `staff_login` لا يزال مغلقًا إلى حين cutover.
5. اختبر العضو القديم: تطابق المعرّف والحقول والمحتوى والنقاط قبل/بعد؛ تكرار الربط لا يكرر العضو؛ العنوان المعدّل بلا دليل لا ينقل الحساب؛ الحساب المحظور لا يعود بالتأكيد.
6. انشر نسخة الواجهة المرشحة على نطاق Staging المعتمد. تأكد أن `auth.js` يُحمّل قبل `common.js`، وأبطل نسخة CDN/المتصفح القديمة عند الانتقال، وتأكد أن المتصفح لا يخزن كلمات المرور/رموز الاستعادة القديمة في جلسة التطبيق.
7. مع استمرار الصيانة، شغّل cutover في **الاتصال/الطلب نفسه** مع الإقرار الصريح التالي، ثم محتوى ملف cutover كاملًا:

   ```sql
   SET cineaura.allow_security_cutover = 'on';
   -- يلي ذلك كامل sql/auth_cutover.sql، لا جزءًا مختارًا منه.
   ```

   لا تعتمد على استمرار اتصال SQL Editor بين تشغيلين منفصلين. كل ملف معاملة واحدة؛ أي خطأ يوقف مرحلته. تحقّق من الفشل ونفّذ `ROLLBACK` عند الحاجة قبل الإصلاح. سيُرفض cutover دون مراجعة مستقلة مطابقة للموظفين وSuper Admin مربوط ومؤكد وغير محظور.
8. راجع `cineaura_private.rpc_manifest` من الإدارة: القرار والتعريف الأصلي والغلاف لكل دالة. في تركيب الاختبار غُلّفت **206 overloads**، لكن العدد ليس شهادة بمراجعة دلالات كل دالة. أي دالة أو سلوك غير مراجع يبقى مغلقًا. عند انحراف تعريف دالة مغلفة، تتوقف إعادة التطبيق بـ `rpc_definition_drift` بدل مضاعفة الغلاف.
9. اختبر الأدوار الحقيقية عبر GoTrue/PostgREST، لا SQL فقط: زائر؛ عضو A؛ عضو B؛ محظور؛ موظف محدود؛ مشرف. جرّب المعرّف والرمز المسروقين من fixtures فقط، وطلبات الأعمدة المباشرة والحقول المحمية.
10. تحقق من العمليات المسموحة والمرفوضة ورسائل فشل الواجهة ومهام الخلفية. اجرد الدوال المعطلة والتغييرات في ACLs قبل رفع الصيانة.
11. بعد نجاح Staging والموافقة التشغيلية، كرر الخطة الموثقة في نافذة الإنتاج مع نسخة احتياطية حديثة والتحقق بعد النشر. لا تنقل مصادقات أو موافقات Staging إلى أعضاء الإنتاج تلقائيًا.

لا يُعاد تشغيل `auth_contain.sql` الأولي بعد الإغلاق؛ يُرفض ذلك حتى لا يتحول إجراء التثبيت إلى توقف مفاجئ غير مخطط. الحوادث اللاحقة تحتاج خطة احتواء مستقلة ومراجعة تشغيلية. إعادة `auth_cutover.sql` مشروطة بثبات تعريفات الدوال ومراجعة قائمة الموظفين، ولا تعيد فتح ميزات غير مراجعة.

### مصفوفة التوافق — ما لا يجوز إخفاؤه بفتح الصلاحيات

| المسار | حالة المرشح/القرار |
|---|---|
| دخول/تأكيد/ربط/استكمال ملف/استعادة | مطبق؛ اختبارات موفر تجريبي ومتصفح ناجحة؛ يحتاج تجربة GoTrue وبريد حقيقيين |
| قراءة ملف العضو وتعديل النصوص المسموحة | قائمة أعمدة وسياسات ملكية؛ لا كتابة مباشرة للهوية أو الخطة أو النقاط |
| الرسائل والإشعارات | عزل الأطراف/المتلقي؛ لا INSERT اعتباطي للإشعارات ولا تغيير جسم/هوية رسالة عبر UPDATE |
| أول تفعيل Free | دالة أصلية ذرّية؛ مرة واحدة ولخطة Free فقط؛ لا تمديد مجاني لخطط مدفوعة |
| شراء خطة بالنقاط | اختبار محلي للدالة الفعلية ودفتر الصرف؛ ليس اختبار دفع خارجي |
| السحب | هوية وربط وإعادة تحقق حديثة؛ اختبارات الرفض محلية، **لا صرف مالي حقيقي ولا تأكيد نجاح تحويل خارجي** |
| إدارة الحسابات | ملكية رمز الموظف وإذن Accounts وتسلسل الأدوار/حالات صحيحة؛ بقية إجراءات اللوحة تحتاج اختبارًا مسارًا بمسار |
| جداول/طرق نشر ومتابعة وتقارير وقوائم ومجتمع/متجر غير مضافة إلى السماح | **مغلقة افتراضيًا**؛ الواجهة القديمة قد تتلقى رفضًا. إضافة السياسات الآمنة والاختبارات شرط قبل إعادة فتح كل مسار |
| بعض RPC المساعدة أو غير المصنفة | خادم فقط أو معطلة للمتصفح؛ لا تعيد EXECUTE عامًّا لإخفاء الخطأ |
| Storage والرفع/التنزيل الخاص | احتواء مؤقت: كتابات المتصفح والقراءات الخاصة غير المراجعة مرفوضة؛ ملكية الملفات والماسح والمراحل الموقعة تحتاج إصلاحًا مستقلًا تاليًا |
| Patreon / النشر الخارجي / YouTube / تشغيل IPTV | ليست موثقة طرفًا لطرف بهذا الإصلاح؛ راجع دلالات معرّف العضو ومعرّف المزود والإعدادات قبل تعديل Edge أو تفعيل المطالبات/النشر |

في تكامل Patreon الحالي، `p_user` هو معرّف Patreon الذي يعيده OAuth، و`p_account` تسمية/مفتاح مراجعة لحساب Patreon، **وليس معرّف عضو CineAura**. لا تستبدله بـ `member_id` دون تصميم حقل ربط مستقل ومراجعة المطالبات القديمة والتعارضات. إبقاء Edge دون تعديل هنا ليس توثيقًا لسلامة شروط الدفع أو ربطه بالعضو.

بعض دوال القراءة العامة ما زالت مصممة لعرض بيانات الكتالوج/المستوى العامة، وليس سجلات الرسائل أو السحب. لا تعتبر التغليف الآلي مراجعة كاملة لقواعد الأرباح أو بلد الإقامة أو مزود خارجي. **لا تُفعّل ميزة إنتاج حساسة إلا بعد اختبار قواعدها نفسها.**

## 6. حدود احتواء Storage والمنح المستقبلية

- سياسات `AS RESTRICTIVE` تُضاف فوق السياسات الموجودة لأدوار `anon` و`authenticated`، لمنع بقاء سياسة قديمة تسمح بالكتابة أو قراءة الملفات الخاصة.
- لا تُحذف ملفات أو buckets ولا تتغير أعلام `public` بهذا الإجراء. **روابط الملفات في buckets العامة تظل عامة**. كذلك لا تفترض إلغاء الروابط الموقعة الصادرة مسبقًا قبل انتهاء صلاحيتها؛ افحص سياسة الإبطال/النقل لكل حالة.
- يبقى `service_role` للعمليات الخلفية الموثوقة. لا تستخدمه لحل مشكلة صلاحيات من المتصفح.
- `ALTER DEFAULT PRIVILEGES` يضبط افتراضات **دور التنفيذ**. راجع بقية أدوار إنشاء الكائنات/المهاجرات و`pg_default_acl` واضبطها إداريًا أيضًا. إعادة تشغيل مثبت قديم أو منح امتيازات صريحة لاحقًا قد يعيد الثغرة.
- قائمة أعمدة دليل الملفات الشخصية قائمة سماح؛ أي عمود جديد يحتاج قرار خصوصية واختبارًا صريحًا قبل ظهوره.

## 7. تشغيل الاختبارات وإعادة إنتاج النتائج

الرسائل الجديدة مغطاة بالعربية والإنجليزية؛ تستخدم بقية اللغات fallback الإنجليزي إلى حين استكمال ترجمتها.

يتطلب التشغيل Node.js 22+ وبيئة قادرة على تشغيل PostgreSQL وChromium. المكتبات **للاختبارات فقط** ومثبتة الإصدارات في lockfile، وليست تبعيات تحميل لواجهة الموقع:

```bash
npm ci
npm test

# أو على حدة:
npm run test:auth
npm run test:auth:source
npm run test:security:db
npm run test:auth:browser
```

اختبار المتصفح يستخدم Chromium المرفق لـ Linux؛ على منصة أخرى يمكن تحديد متصفح مثبت:

```bash
CHROMIUM_PATH=/absolute/path/to/chromium npm run test:auth:browser
```

يُفتح لكل سيناريو متصفح مستقل لتفادي تعطل دورة سياقات Chromium serverless. كل طلب داخل الاختبار معترض، بما فيه Auth وقاعدة البيانات والبلد والصور والخدمات الخارجية؛ لا يُنشأ حساب حي. `AUTH_SCENARIO` يتيح تشغيل سيناريو محدد للتشخيص؛ التشغيل الكامل لا يضبطه.

### نطاق التحقق

- **24 اختبار عميل**: عدم استعمال API key كـ Bearer، عدم الرجوع للاعتماد القديم، PKCE وصلاحية الحالة، حدود إرسال الرموز، التحديث والتجديد والإبطال وسباقات الجلسات، ومنع إعادة الطلب بهوية أخرى أو إعادة إرسال عملية Edge ذات أثر جانبي عند رفض المزود.
- **33 مجموعة PostgreSQL**: 65 ملف مخطط فعليًا داخل PostgreSQL 17 مؤقت؛ الاحتواء قبل التقاط الهوية ومراجعة امتيازات الموظفين، واعتماد الملكية وإثبات البريد الحديث، حفظ البيانات، المنح والأعمدة والسياسات، عزل الرسائل، منع انتحال الفاعل، شراء عضوية بالنقاط ودفترها، شرط السحب، الموظفون والتسلسل الإداري، Storage، وتكرار الانتقال. يختبر أيضًا إبطال رموز اللوحة القديمة وعدم نشر أعمدة ملف شخصي جديدة تلقائيًا.
- **8 سيناريوهات Chromium**: جلسة محلية مزورة؛ فشل الدخول دون fallback؛ دخول أصلي وجلسة مؤقتة؛ ربط قديم مع الاحتفاظ بـ ID؛ استكمال اسم مستخدم بعد التأكيد دون تسجيل ثانٍ؛ الاستعادة وتطابق كلمة المرور؛ رفض المحظور؛ عناوين عربية على الهاتف.
- **فحوص المصدر**: تحليل صياغة JS/HTML-inline/TS، ترتيب التحميل، المرايا والترجمات، وعدم إعادة أنماط الاتصال القديمة. تحليل TS هو تحليل صياغة، وليس تشغيل Deno أو فحص أنواع/تكامل المزود.

في الاختبار المحلي تُحاكى `auth.uid()` و`auth.jwt()` و`auth.role()`، ولا يحدث تحقق توقيع JWT حقيقي في PostgreSQL التجريبي. نجاحه **لا يثبت** تكامل GoTrue أو إصدار AMR أو تسليم البريد أو الإعدادات أو تحصيل/صرف مال أو رفع ملف أو نشر محتوى خارجيًا في الإنتاج.

## 8. التحقق بعد الإنتاج والتراجع الآمن

### لا تعلن إغلاق P0 قبل التحقق التالي

- لا يستطيع الزائر أو العضو قراءة `members.password`/`recovery_code` أو تعديل حساب آخر أو خطته أو نقاطه، حتى عبر الطلبات المباشرة والعروض القديمة ومنح الأعمدة.
- لا يستطيع العضو A رؤية رسائل/إشعارات B أو تنفيذ RPC باسمه أو استخدام رمز موظف آخر. الحظر يوقف الصلاحيات حتى مع JWT لم تنته صلاحيته.
- يمكن لمالك حساب قديم مُراجع إثبات البريد والعودة إلى **المعرّف والمحتوى والنقاط نفسها**. يبقى غير المراجع معلقًا، ولا يُنشأ بديل له.
- تعمل جلسة المشرف المحدود بالصلاحيات المقررة فقط، ويوجد وصول Super Admin موثوق، ولا يعمل bootstrap العام.
- تعمل الميزات التي قُرر السماح بها، وتظهر الميزات المعطلة بوضوح؛ لا نجاح وهميًا عند رفض الطلب ولا إعطاء صلاحيات عامة لتمرير الاختبار.
- قورنت أعداد الملكيات والمحتوى والأرصدة والمنح بالنسخة السابقة من إدارة موثوقة، مع تدقيق لا يسجل كلمات مرور أو JWT أو بيانات رسائل.
- اختُبرت الروابط الحقيقية والبريد وتجديد الجلسات وPostgREST وStorage والخلفيات في بيئة النشر، ووُثقت النتيجة الفعلية.

### إذا فشل الانتقال

1. أبقِ الصيانة ومنع الوصول غير الموثوق قائمين. لا تسترجع `USING (true)` أو منح CRUD/EXECUTE العامة كحل سريع.
2. إن فشلت معاملة SQL قبل `COMMIT`، تأكد من `ROLLBACK` وحالة الاتصال؛ لا تعتبر ملفًا منفذًا جزئيًا نجاحًا.
3. إن فشل التطبيق بعد إغلاق ناجح، أصلح للأمام أو أعد إصدارًا متوافقًا مع الحماية. الواجهة القديمة وحدها ليست تراجعًا صالحًا لأنها تعتمد على الصلاحيات القديمة.
4. لا تعكس خريطة UUID أو ledger أو الأرصدة يدويًا. عند الضرورة، استعد النسخة المختبرة **في بيئة معزولة**، وفك تعارض أي كتابة لاحقة، ولا تعد الخدمة العامة قبل استعادة الحواجز والتحقق.
5. احتفظ بمرجع الموافقات وmanifest والتغييرات وسجل التنفيذ داخل إدارة آمنة. لا تنشر تعريفات التشغيل الحاوية أسرارًا أو نسخ بيانات المستخدمين مع ملفات الموقع.

**الأولوية التالية بعد تثبيت هذا الحاجز والتحقق منه:** ملكية Storage ومسار الرفع/الفحص/التنزيل، ثم الكتابات والنشر الحقيقي والتكاملات بحسب خطورة نتائج تقرير التدقيق. لا تنتقل إلى تحسينات شكلية على حساب بقاء P0 مفتوحًا.
